# CATS development and deployment

Generated by OpenAI Codex on 2026-11-01.

Compose describes a group of containers, how they communicate, and where their data
lives. `compose.yaml` is shared; Make selects explicit overlays so local debug
ports never accidentally become production ports. No changes to DEMO_PLAYGROUND
are needed. These files deploy the current main application, not the older demo.

## Three workflows

| Command | Result | Stop |
| --- | --- | --- |
| `make dev` | Local PostgreSQL/PostGIS at localhost:15434; FastAPI reload at localhost:8000; Expo at localhost:8081 | Ctrl-C, then `make dev-down` |
| `make stack-test` | All three images, served at http://localhost:18082 | `make stack-down` |
| `make deploy SSH_KEY=/absolute/path/key.pem CATS_TAG=release-id` | Upload already-built ARM64 images over administrator SSH; start rootless server stack on localhost:18082 | Administrator operates server Compose |

Run `make setup` once to install host dependencies. Docker Desktop must be running.
The dev supervisor shuts down both reload processes when either exits; the DB
stays running. Development and stack tests use different Compose projects and
volumes. Neither points at production. The original `cats_cats_data_pg18` and
older volumes are left untouched; the new workflows initialize fresh volumes.
Use dump/restore if you need their contents. Never use `down -v` on valuable data.

The browser container uses `/api` relative URLs. Local Expo defaults to
http://localhost:8000/api; set EXPO_PUBLIC_API_URL to a reachable URL ending in
`/api` for phones/native builds. Static web settings are embedded at build time.
Backend routes, including docs and health, are consistently under `/api`.

`make stack-check` checks the static frontend, API health, and locations backed by
PostGIS. Each new database initializes PostGIS and an empty locations table.
`uv run python scripts/add_locations.py` seeds only the local dev DB by default.
The app DB role is not a PostgreSQL superuser. Admin credentials are different.
Initialization runs only for new volumes: changing env passwords does not rotate
existing database passwords. Future schema changes need explicit versioned
migrations; initialization SQL is not a migration runner.

## PostgreSQL and CPU architecture

The database is PostgreSQL **18** plus PostGIS **3.x** (PostGIS itself has no version
18). The upstream postgis/postgis image is AMD64-only. Our Dockerfile uses the
official multi-architecture postgres:18-trixie image and official PGDG PostGIS
packages instead. No x86 emulation is required on ARM Macs or the server.

## Build and release

```
make validate test-api
make stack-test
make release-build CATS_TAG=<commit-or-release-id>
make deploy SSH_KEY=/absolute/path/to/key.pem CATS_TAG=<same-id>
```

The deploy target uploads prebuilt images, installs reviewed Compose files as
root-owned, and starts containers. It does not configure DNS, enable a public
Nginx site, or grant classmates access. It requires your admin SSH key; never
share that key with classmates. Build the ARM64 release locally or in CI. The
server has limited CPU/memory and should not build images.

`make release-save` optionally writes an image archive in ignored `work/`.
On the server, `make -f /etc/cats/Makefile server-up CATS_TAG=<id>` is the equivalent
start command when run as catsdeploy. `server-status` and `server-backup` use the
same fixed admin-owned Compose files. Specify the release tag for status/backup
as needed. Retain older image tags for rollback; a rollback must also be compatible
with the current schema. Do not downgrade the PostgreSQL major version in place.

## Server preparation and security boundary

An administrator runs `deploy/provision-server.sh` as root on Ubuntu. It creates
catsdeploy with a locked password and no SSH keys, installs rootless prerequisites,
starts a dedicated Docker daemon, and generates random production credentials in
/etc/cats/production.env (root-owned, group-readable only by catsdeploy).

The user slice caps all CATS processes at 1 GiB memory, 128 MiB swap, half a CPU,
and 512 tasks. Compose adds per-container limits. An nftables table affects only
the catsdeploy UID: it rejects new connections to host/private/link-local addresses
and EC2 metadata, permits DNS through the host resolver, and disables IPv6 egress.
It permits established response traffic so host Nginx can reach the app. The host
public address is resolved at provisioning; refresh the rules if it changes.
Existing Docker services and firewall tables are not replaced.

This remains a shared kernel and filesystem. The entire CATS home is now bounded by an 8 GiB filesystem. Classmates use the
separate forced-command SSH accounts described in ACCESS.md; they never receive
unrestricted shell or Docker access. The admin deployment command remains admin-only. UID filtering
also does not make arbitrary uploaded code safe or protect against kernel exploits.
Use a separate VM for a strong boundary against hostile code.

The API image runs without root and has no host mounts or Docker socket access.
PostgreSQL has no published host port. Only the frontend binds to localhost:18082.
Production secrets never enter image builds or Git. CATS backend code necessarily
can read its own database credentials and data.
