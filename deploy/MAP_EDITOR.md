# Database-backed campus map

Generated by OpenAI Codex on 2026-11-03.

## Run locally

Start Docker Desktop, then run `make dev` (or the `make map-editor` alias).
`db-up` applies the users and map migrations and imports the campus source only
when the map database is empty. Open http://localhost:8081/maps or the **Map editor**
tab. Restart an already-running development frontend after changing this code.

PostgreSQL is authoritative after the initial import. Editing the OSM source file
will not overwrite database edits on restart. `make map-import` is idempotent and
skips populated datasets. The `.osm` file is retained as source provenance; it is
not shipped to browsers or read by the frontend. Existing application tables are
unchanged.

## What's stored

Every source node, way, relation, and tag is imported, including bicycle racks,
parking lots, paths, benches, entrances, and buildings. UUID-based feature IDs are
stable across repeated imports of the same source IDs. `object_type` and `osm_id`
retain source identity; new features have UUIDs and no fabricated OSM ID.

- `map_features`: tags/source tags, point coordinates, PostGIS geometry, stable
  building links, geometry/link review statuses, and record versions.
- `map_refs`: ordered node and relation references. Missing references outside
  the source extract remain recorded with a null target instead of being dropped.
- `map_names`: main, alternative, short, official, and old names for indexed search.
- `map_dataset`: global revision and original import digest.
- `map_changes`: actor, timestamp, revision, and before/after records for each save.

Original tags remain in `source_tags`. A resolved `entrance:building` label is
removed from active tags and replaced by the `building_id` foreign key. Matching
uses exact normalized names/aliases and actual outline membership. Contradictions,
unknown names, and multiple matches remain unlinked/ambiguous for human review.
Changing a building name does not change its ID or entrance associations.

## Query APIs

All endpoints require the existing application login in production.

- `GET /api/map/features?bbox=west,south,east,north`: GeoJSON for a map viewport.
- `GET /api/map/features?q=Park`: match primary or alternative names.
- `GET /api/map/features?tag_key=amenity&tag_value=bicycle_parking`: query arbitrary tags.
- `GET /api/map/features?tag_key=amenity&tag_value=parking`: parking areas/points.
- `GET /api/map/features?kind=building` or `kind=entrance`: typed filters.
- `GET /api/map/features/node/<uuid>` (also `way`/`relation`): selected feature detail.
- `GET /api/map/permissions`: whether the current identity may edit.
- `GET /api/map/editor`: editor-only JSON topology snapshot and dataset revision.
- `POST /api/map/editor`: editor-only atomic changeset with revision, upserts, deletes.

GeoJSON results are paginated with `limit` (maximum 2000) and `after`; follow the
returned `next` cursor until null. The viewer follows all pages and uses feature IDs
for click details. It never needs to guess an object from click coordinates.
Incomplete geometry is retained in the editor graph and flagged, but cannot appear
as geometry in the viewer. Non-spatial relations are preserved in the graph.

## Editing permissions and controls

The backend allows `tufts1cr@cmich.edu` by default. Administrators can set
`CATS_MAP_EDITOR_EMAILS` to a comma-separated list of approved verified-account
emails. `developer@example.test` is additionally allowed only when authentication
is disabled for local development. Production identity comes from the validated
session, never request JSON or an email submitted by the frontend. Origin checks
protect mutations. The tab is hidden for other users; the API independently
rejects their reads of the editing snapshot and all writes.

Select an object to edit tags, add/remove/drag vertices, insert entrance nodes,
or delete it. Draw new building/parking/area outlines or place points. All tags,
including variable attributes such as bike-rack capacity, remain editable.

Entrance nodes have a building dropdown showing stable IDs. Review unlinked or
ambiguous entrances there. Referenced objects and buildings with linked entrances
cannot be deleted until their references are removed/reassigned. Shared vertices
are locked until explicitly detached; detaching disconnects shared topology.
Relation tags can be edited and member ways selected, but creating multipolygon
holes or rewriting arbitrary relation memberships is not implemented.

Apply tag edits before saving. Undo/redo apply to the last ten draft operations;
saving resets that draft history. **Export draft** downloads JSON for recovery.
**Save to database** submits only changed records, regenerates dependent geometry,
and records an audit entry in one transaction. Invalid geometry/new dangling
references are rejected. A revision conflict returns 409 instead of overwriting
another editor. Export your draft and reload to reconcile a conflict.

Background raster tiles are independent and remain read-only. Toggle them off to
inspect only database features. Refresh the viewer after a save.

## Production rollout and recovery

These instructions do not deploy changes automatically. Before deployment:

1. Take the existing PostgreSQL backup, using the established server backup workflow.
2. As the database administrator, apply `deploy/migrations/004_map.sql` (and 003 if
   it has not already been applied).
3. Run `python scripts/import_campus_map.py --if-empty` with the target database
   environment and the intended source dataset. Review link/geometry counts.
4. Deploy the API and frontend together. Confirm the editor email allowlist and
   authenticated reads/writes. The runtime database role has DML, not schema rights.

The normal off-server database backups include map tables and audit history.
A saved edit can be reviewed in `map_changes`; an administrator can reconstruct
an inverse changeset from `before_state` and submit it against the current revision,
or restore a database backup. There is no automatic “restore old revision” button.
Do not blindly replay old records over later edits; dependencies must be reviewed.

Walking topology is preserved, but this change does not calculate routes, infer
walkable connectors, or validate accessibility. Disconnected entrances and access,
steps, level, and crossing restrictions still need review before routing is enabled.

## Checks

`make validate test-api test-map-editor` runs the standard checks and JSON graph
editing tests. For actual PostGIS transaction/query tests, set
`MAP_TEST_DATABASE_URL` to an administrator connection for a **local test database**
and run `PYTHONPATH=back_end/app uv run pytest tests/backend/test_map_postgis.py`.
Tests create and drop uniquely named schemas without modifying the campus tables.
